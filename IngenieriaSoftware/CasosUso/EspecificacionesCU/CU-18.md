### Caso de Uso 18 (CU-18)
* **Nombre:** Gestionar Alertas y Seguimiento Crítico
* **Descripción:** el gestor consulta en una vista independiente los especímenes desnutridos o enfermos y navega desde cada registro a su ficha para resolver el estado crítico.
* **Actores:** Gestor del Zoo
* **Precondición:** existe una partida seleccionada y el sistema puede consultar las alertas de salud y los estados vigentes de los animales.
* **Postcondición:** el sistema presenta el seguimiento crítico actualizado y, si el gestor selecciona un espécimen, abre su ficha sin alterar por ello el estado del parque.
* **Situaciones de Error:** no se pueden recuperar las alertas o el estado actual de un animal, o el espécimen dejó de ser elegible antes de abrir su ficha.
* **Situación del Sistema en caso de Error:** el sistema no inventa ciclos ni conserva como vigente una alerta cuyo estado actual no pudo validar. La consulta y la navegación no modifican animales, alertas, métricas ni ciclos.
* **Flujo Básico:**
  1. El gestor abre el panel de seguimiento crítico, independiente de la bitácora general.
  2. El sistema consulta los animales vivos con alimentación al 0% o en estado enfermo y agrupa los registros según el estado crítico correspondiente.
  3. Para cada espécimen, el sistema presenta su nombre descriptivo, el estado crítico, los ciclos acumulados y los ciclos restantes antes del límite de defunción aplicable. Si coinciden desnutrición y enfermedad, muestra los contadores independientes y utiliza el mayor para determinar el límite.
  4. El sistema representa cada alerta simultáneamente mediante color, iconografía distintiva y texto explícito, sin exponer identificadores internos.
  5. El gestor selecciona un registro y solicita abrir la ficha técnica del espécimen.
  6. El sistema vuelve a validar que el espécimen y el estado seleccionado siguen vigentes y abre la ficha con las acciones que correspondan: alimentar si tiene hambre activa o aplicar tratamiento si está enfermo.
  7. El gestor puede ejecutar la acción en el flujo de alimentación o tratamiento; el panel refleja los cambios cuando se actualiza por el evento correspondiente.
* **Flujo alternativo:**
  * **1.a: no hay alertas críticas activas.** El sistema muestra que no hay especímenes que requieran seguimiento y no crea registros de alerta.
  * **2.a: una alerta ya no coincide con el estado persistido del animal.** El sistema excluye la alerta obsoleta y presenta el estado vigente.
  * **2.b: no se pueden recuperar los ciclos acumulados o restantes.** El sistema identifica el dato no disponible y no calcula un plazo supuesto.
  * **3.a: los contadores de desnutrición y enfermedad son distintos.** El sistema los mantiene diferenciados y usa el contador mayor para el límite conforme a la regla definida.
  * **5.a: el gestor vuelve al panel sin seleccionar un espécimen.** No se realiza ninguna mutación ni recálculo.
  * **6.a: el espécimen murió, fue vendido o dejó de tener el estado crítico antes de abrir su ficha.** El sistema no inicia una acción obsoleta y actualiza o retira el registro del panel según el estado confirmado.
  * **6.b: falla la navegación a la ficha.** El sistema conserva el panel y no altera el espécimen ni su alerta.
  * **7.a: el gestor necesita alimentar o tratar al espécimen.** El sistema deriva al flujo correspondiente; solo la acción confirmada modifica inventario, estado, alertas y métricas.

### Puntos pendientes
La configuración puede dejar pendientes valores biológicos y fórmulas de métricas; esta vista muestra los contadores persistidos y no calcula valores sustitutivos. Las condiciones para resolver una alerta se aplican únicamente según las reglas confirmadas de alimentación, tratamiento y simulación.
