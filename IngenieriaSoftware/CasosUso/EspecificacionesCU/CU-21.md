### Caso de Uso 21 (CU-21)
* **Nombre:** Consultar Historial de Avisos
* **Descripción:** el gestor consulta la bitácora cronológica de avisos del zoológico, diferenciando notificaciones informativas, operativas interactivas y alertas críticas de salud.
* **Actores:** Gestor del Zoo
* **Precondición:** existe una partida seleccionada y el sistema puede consultar los avisos persistidos.
* **Postcondición:** el sistema presenta los avisos disponibles en orden cronológico y con su clasificación y estado, sin alterar su contenido ni ejecutar acciones por el hecho de consultarlos.
* **Situaciones de Error:** no se puede recuperar el historial o faltan datos para clasificar o presentar un aviso.
* **Situación del Sistema en caso de Error:** el sistema informa de la consulta fallida y no transforma ni elimina registros. No asigna categorías, fechas, severidades o estados supuestos.
* **Flujo Básico:**
  1. El gestor abre la vista del historial de avisos.
  2. El sistema recupera los avisos persistidos de la partida y los presenta en orden cronológico.
  3. Para cada aviso, el sistema muestra la fecha disponible, el contenido descriptivo, la categoría, la severidad cuando corresponda y el estado persistido, sin exponer identificadores internos.
  4. El sistema diferencia visual y funcionalmente:
     * Avisos informativos no interactivos, como ascensos de prestigio o desbloqueos de especies.
     * Notificaciones operativas interactivas, que pueden incluir una acción cuando siga vigente.
     * Alertas críticas de salud, diferenciadas mediante código de color, iconografía y texto explícito.
  5. El gestor consulta los avisos. Listar la bitácora no marca, descarta, acepta ni resuelve ningún aviso. Abrir el detalle de un aviso `PENDIENTE` es una acción explícita que lo marca como `VISTA`; no lo acepta, descarta ni resuelve, no ejecuta su acción y no provoca recálculos de simulación.
  6. Si el gestor selecciona una acción de un aviso operativo vigente, el sistema valida su vigencia y navega al flujo o vista correspondiente; la acción de dominio se confirma únicamente en su caso de uso específico.
* **Flujo alternativo:**
  * **1.a: no existen avisos persistidos.** El sistema muestra el historial vacío sin crear avisos.
  * **2.a: ocurre un error al recuperar una parte del historial.** El sistema informa del problema y no presenta como completo el contenido que no pudo cargar.
  * **3.a: un aviso carece de fecha, categoría o estado legible.** El sistema señala el dato no disponible y no inventa su valor ni reclasifica el aviso.
  * **4.a: el aviso es informativo.** El sistema lo presenta como no interactivo, sin ofrecer una acción de aceptación o resolución.
  * **4.b: el aviso es una notificación operativa pero ya no está vigente.** El sistema conserva su registro histórico y no ofrece una acción que ya no corresponda.
  * **4.c: el aviso es una alerta crítica de salud.** El sistema mantiene su clasificación crítica y permite consultar el seguimiento vigente sin sustituirlo por una notificación informativa.
  * **6.a: el aviso deja de estar vigente antes de accionar su acceso.** El sistema vuelve a validar el estado, conserva el historial y no ejecuta la acción obsoleta.
  * **6.b: falla la navegación al flujo correspondiente.** El sistema conserva la vista del historial y no altera el aviso ni el estado de la partida.

### Reglas y valores aplicables
Severidad fija por clase: informativa `BAJA`, operativa `MEDIA`, crítica `ALTA`. Las transiciones de estado están en `EspecificacionBBDD.md` (sección 2.3.2): al abrir el detalle de un aviso `PENDIENTE` pasa a `VISTA` (final para los informativos); listar la bitácora no cambia ningún estado y abrir un aviso no ejecuta ni cierra su acción ni dispara recálculos. La bitácora es una ventana acotada de avisos (los pendientes siempre se conservan), no un histórico indefinido.
